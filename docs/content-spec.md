# 内容规范 · history-kb

> 状态：**草案，待 Rick 确认**　|　2026-07-12
> 用途：M5 全量内容重扫的验收标准。GLM 按此重扫，校验器（validate_data.py）升级为 linter 强制执行，Claude 10% 抽查史实。
> 立意：回应"内容过简"——让每条数据不只有"是什么"，还有"为什么相关/怎么回事"，且可追史料。

---

## 1. 关系必须表达"关联逻辑"（核心）

**问题**：现有关系要么无 `note`（1099 条），要么是模板化套话（CBDB "收到Y的赠诗、文"）。卡片能显示"苏轼—欧阳修 associated_with"，但读者不知道**他们因何相关**。

**规范**：
- **语义关系必须带 `note`**——一句话说清关联逻辑（谁、因何、与谁、发生了什么）。
  - 反例（禁止）：`associated_with`（裸）、"有交往"、"收到Y的赠诗"
  - 正例：`欧阳修 → 苏轼 [荐举] note:"嘉祐二年知贡举,识拔苏轼,叹'当避此人出一头地'"`
  - 正例：`王安石 → 司马光 [政敌] note:"熙宁变法中司马光领旧党力争,罢相后作《资治通鉴》"`
- **自明关系豁免 note**（不强制）：`father_of`/`mother_of`/`spouse_of`/`sibling_of`/`child_of`（亲属，类型即含义）；但若有特殊背景可加（如"庶出""继室"）
- **半自明关系建议带 note**：`served_under`/`mentored_by`/`member_of`（说清何时何事）
- **CBDB 模板化 note 升级**：`associated_with` 尽量替换为更具体的关系类型（荐举/唱和/论敌/姻亲/同僚）+ 具体 note；无法考证具体的，保留 associated_with 但 note 写明可考的最小事实，不用纯套话

## 2. 人物生平结构化

- `bio`（保留）：一段叙述性小传（现有多数已有，重扫时补全过简的）
- **新增 `life_events[]`**：大事记数组，每项 `{year, event, source?}`——年份 + 一句话事件 + 出处
  - 例（李白）：`[{year:742, event:"奉诏入长安,供奉翰林"}, {year:744, event:"赐金放还,离长安"}, {year:757, event:"入永王李璘幕,兵败系狱"}, {year:762, event:"卒于当涂"}]`
- **覆盖范围（待 Rick 定,见 §6）**：建议 importance 1（核心）必填 life_events，importance 2（重要）建议填，importance 3/CBDB 只保证 bio 不强制 life_events

## 3. 各类型字段最低标准

| 类型 | 必填 | 建议 |
|---|---|---|
| Person | name, born/died(或标"约"/缺考), birthplace, sources；核心+重要须 roles+importance | life_events, alias, bio |
| Event | name, date, category, description, sources；战乱/变法类须 impact + 因果关联(caused_by/led_to ≥1) | end_date(跨年), location |
| Battle | name, date, location, 双方(combatants), 结果, sources | significance, commanders |
| Polity | name, founded/fell, 都城, sources | 疆域 territory |
| Faction | name, description(说清主张/构成), sources | 关键成员关系 |

## 4. 出处格式规范

- 正史：`书名·卷/纪传名`，如 `史记·秦始皇本纪`、`资治通鉴·卷210`、`旧唐书·玄宗本纪`
- 数据库：`CBDB`、`CHGIS`（保留来源标识）
- 现代研究：`作者·书名`，如 `陈寅恪·唐代政治史述论稿`
- 存疑：史源冲突时 `note` 标 `disputed:true` + 说明；日期不确定标"约"

## 5. 身份/重要性标注标准（T4.0 已定义,此处固化判据）

- **roles[12]**：帝王/宗室/后妃/外戚/将领/文臣/学者/文人/宦官/起义领袖/僧道/隐逸（可多标；客观可判,不确定留空不硬猜）
- **importance**：`1 核心`（教科书级家喻户晓,约 60-80 人）/`2 重要`（正史有传、专业者熟知）/`3 一般`（CBDB 次要人物默认档）

## 6. 重扫范围与批次（待 Rick 定——决定工程量与配额）

**方案 A（推荐·分层）**：
- 种子 419 人 + 122 事件 + 34 战役 + 28 派系 + 55 政权：**全部升级到规范**（关系补 note、生平结构化、字段补全）
- CBDB 4892 人：只保证 bio 不强制 life_events；其 associated_with 关系**只补核心人物圈层**（如朱熹/苏轼/李白等 links 高的 Top 圈,约数百条），不全量 9010 条重写
- 扩容：事件 122 → 300+、战役 34 → 80+（新增即符合规范）

**方案 B（激进·全量）**：CBDB 9010 条关系全部补语义 note——工程量大、配额消耗高、史料考证难度高（很多 CBDB 交往无具体可考），性价比低。**不推荐**。

## 7. 数据红线（重扫强制）
- AI 生成必过 linter（校验器升级版）+ sources 必填
- 史实存疑标 `disputed:true`，宁缺毋滥（无出处不硬补）
- Claude 每批 10% 抽查史实，抽查不过整批打回
- 分批进行，每批过闸门后合并；注意方舟 5 小时配额节奏（打满自动降级 Anthropic）

## 8. UI 文案三层规则（PRD 原则 5 固化,D1）

同一屏里繁简并存不是混乱，是分层——各层守各层的规矩，改文案前先认层：

- **品牌层从繁**：紀年圖譜、以時為軸、印章字形（人/國/事/戰/地…）、朝代名（戰國/漢/民國）。这是产品的气质，不简化、不翻译。
- **数据层从史**：人名、地名、年号、引文一律依数据源原样呈现，不做简繁转换、不改写古称（如「碎叶」不写成「托克马克」，modern_name 仅作今名标注）。
- **UI 层从简**：按钮、提示、空态、设置、单位后缀一律简体白话。禁止夹英文残留（` CE`、`Top`、`SCROLL THROUGH TIME` 之类）；负年已由「前」表达，正年直书「750 年」不加后缀。

审查口径：全站 grep 不得出现孤立英文 UI 串（数据自带的英文名除外）；新增 UI 文案一律走简体；新增印章/朝代名走繁体。
