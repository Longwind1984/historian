# Exploration v4 Presenter Mode 方案

> 角色：Product Manager Team · 发布体验
> 结论：当前的「设计标注」只是一套可查阅的注释索引，**不是一次产品发布，也不足以构成验收**。它告诉观众组件是什么，却没有建立“为什么存在—如何协作—怎样失败—凭什么批准开发”的叙事。
> 本文只定义 Presenter Mode，不改原型或生产代码。

## 1. 发布会必须讲清的产品命题

开场不能从按钮和三栏布局讲起。Presenter 必须先给观众一个可以复述的产品判断：

> 今天我们发布的不是历史聊天机器人，也不是给静态地图加一层 AI。
> 我们把一个模糊的历史兴趣，变成一份由用户确认范围、由证据约束、可以沿时间和地图播放、也可以随时回到原文核查的探索对象。
> 对话负责立题，编织负责成形，播放负责理解变化，书籍态负责忠实进入作者的论证。三种界面，共享同一份研究上下文。

发布会结束时，观众必须能回答五个问题：

1. 为什么「探索」是一级模块，而不是右栏聊天框；
2. 为什么编织态、播放态、书籍态是一份 Exploration 的三种空间重心；
3. 地图、时间、结构与证据如何在同一个 Scene 上同步；
4. 系统怎样区分史实、作者判断、模型推断、材料关系和证据缺口；
5. 加载、空、失败、地点不确定、网页受限时，为什么产品仍然可信且可继续。

## 2. 三种真正不同的讲解框架

### 框架 A：发布会导演台（推荐）

一条有明确高潮的 Keynote 主线直接运行在真实原型上。画面按章节自动切换到编织、播放和书籍态；聚光遮罩只强调当前区域；右下角是一张克制的 Presenter Card，讲清定位、选择和状态。每章结束，观众可以“接管原型”，再一键回到讲解断点。

**优点**

- 有完整叙事和节奏，能 proud 地说明产品判断，而不是让观众自己猜；
- 讲解发生在真实可操作界面上，设计理由和交互结果同屏；
- 能在最后切换开发视角，把每个讲过的承诺收束到验收清单；
- 同一套 Beat 数据可用于现场发布、录屏、内部评审和开发走查。

**代价**

- 需要维护一套确定性的讲解状态与焦点锚点；
- 内容修改后要同步更新 Presenter Beat；
- 不能把所有注释一次铺开，必须精心编排顺序。

**发布会讲稿骨架**

```text
旧工作台的上限
  → 探索为何成为一级模块
  → 一句话如何成为研究约定
  → 骨架、地图和证据如何被编织
  → 点击播放，历史从知识变成过程
  → 导入一本书，作者论证进入同一时空装置
  → 四类异常证明系统不会“装作知道”
  → 开发批准清单
```

### 框架 B：策展式探索馆

首页是一张“探索装置剖面图”，观众自行选择“提出问题”“播放历史”“进入一本书”“检查可信度”四个展厅。每个展厅是 3–5 分钟的独立微导览，走完后盖章，全部完成才进入开发批准。

**优点**

- 自由度高，适合异步评审和不同角色各取所需；
- 每个展厅可独立更新，不依赖固定发布顺序；
- 对重复访问友好，研究者可直接去“可信度”，设计师可直接去“书籍态”。

**代价**

- 缺少一个强有力的产品高潮，容易重新退化成功能目录；
- 观众可能跳过关键前提，误把三个模式理解为三个小工具；
- Presenter 的主张变弱，比较像博物馆语音导览而不是发布会。

**发布会讲稿骨架**

```text
欢迎进入“历史如何被理解”的四个展厅
  → 立题馆：问题如何成为研究约定
  → 时空馆：Scene 如何在地图和时间上推进
  → 书籍馆：作者判断如何忠实保留
  → 证据馆：材料如何互证、补充、冲突或留白
  → 集齐四章，生成个人验收卡
```

### 框架 C：产品答辩桌

屏幕固定为“左侧真实原型 + 右侧产品合同”。评审按 G/W/P/B 编号审阅；每个区域依次展示默认态、一次关键交互、一个异常态，随后由评审打勾或留下阻断意见。

**优点**

- 完整、可审计，最接近设计交付到开发的验收工作台；
- 状态、数据和 acceptance 可以逐项落到组件；
- 适合工程设计评审，不容易漏边界。

**代价**

- 戏剧性和记忆点最弱，像测试管理工具；
- 先讲编号会遮蔽“大产品为什么成立”；
- 普通观众容易被实现细节淹没，无法感受使用价值。

**发布会讲稿骨架**

```text
产品目标与不可妥协原则
  → G：全局壳合同
  → W：问题编织合同
  → P：播放联动合同
  → B：书籍拆解合同
  → 状态矩阵
  → 逐项批准 / 阻断
```

### 推荐

采用 **框架 A「发布会导演台」**，但在最终章嵌入框架 C 的开发批准清单。原因是本轮失败不在“缺少更多注释”，而在没有形成一条让人理解设计选择的产品叙事。A 先建立信念和整体，再用 C 的合同收口，既像发布会，也能直接进入开发。

## 3. Presenter Mode 的体验合同

### 3.1 入口

- 原型右上角新增内部评审入口「开始产品发布」；不与「设计标注」并列成两个常驻开关。
- 首屏不是说明弹窗，而是覆盖真实产品的开场舞台：
  - 标题：`让历史从知识，变成可以探索的过程`
  - 副标题：`Exploration v4 · Product Walkthrough`
  - 主动作：`开始发布 · 约 12 分钟`
  - 次动作：`自由探索`
  - 辅助动作：`查看章节`
- 发布模式属于 prototype/review build，生产构建移除。

### 3.2 固定舞台元素

1. **Chapter Rail**：左侧 44px 折叠章节轨，只显示 `01 定位 / 02 编织 / 03 播放 / 04 书籍 / 05 信任 / 06 批准`。当前章节展开为标题，已讲章节显示完成。
2. **Spotlight**：对真实 DOM 区域做遮罩、描边和轻微暖色光晕；页面不缩放、不位移，避免“讲解版”与真实版不是同一界面。
3. **Presenter Card**：右下角，宽约 360px，只包含：
   - 一句台上主张；
   - 最多三句解释；
   - `看设计选择`（展开 rationale）；
   - `下一幕`。
4. **Progress**：底部 2px 章节进度，不出现“第 7/27 条产品需求”的工具感。
5. **Live Action Cue**：需要点击时，用一条短动词提示：`现在，选择“军事推进”`、`现在，点击播放`。
6. **Take the wheel**：每章结束出现 `自己试试`，进入自由探索。

### 3.3 镜头和聚焦节奏

每个 Beat 使用同一套五拍，不连续朗读长文：

```text
0.3s  其余界面轻柔降噪
0.4s  聚光移动到目标区域
2–5s  先说“它解决什么”，再说“为什么这样排”
现场动作  触发一次真实交互，让相关区域同帧响应
1.2s  保持结果，给观众看清，再进入下一幕
```

节奏规则：

- 每 3–4 个 Beat 回到一次全局画面，避免观众失去空间感；
- 不用连续飞镜。跨模式只做一次 220–320ms 淡入；
- 地图播放时 Presenter Card 收窄，镜头舞台必须拥有绝对主位；
- 书籍态从左向右讲：原文 → 结构 → 时空 → 证据，符合阅读因果；
- 开启 `prefers-reduced-motion` 时，取消聚光移动和地图飞行，只做瞬时聚焦。

### 3.4 区域标示

现有 G/W/P/B 编号保留为开发索引，但发布会不能让编号成为主叙事。Presenter 使用“可读区域名 + 一句角色”：

```text
研究约定
不是聊天记录，是这次探索的合同

时空地图
不是背景图，是当前 Scene 的空间证据

关系化证据
不凑正反，只描述材料之间真实的关系
```

Presenter Card 展开「看设计选择」后，才显示 `W03 / 默认 / 交互 / 状态 / 数据 / 验收`。这样普通观众先理解产品，开发者仍能定位实现合同。

## 4. 推荐框架的完整发布会

### Chapter 00｜开场：我们为什么重做历史工作台

#### Beat 00.1 — 黑场上的一句话

**屏幕**：只保留品牌、标题和三枚词：`问题 · 时间 · 证据`。
**讲稿**：

> 今天，我们不是给历史知识库加一个聊天窗口。聊天可以回答问题，却留不下一张可以复查、改写和继续探索的历史结构。Exploration v4 要做的，是把你的问题变成一台可操作的时空装置。

#### Beat 00.2 — 从静态库到探索对象

**屏幕**：全局工作台淡入，依次亮起对话、地图、证据。
**讲稿**：

> 原来的时间柱擅长告诉你“某年有什么”。探索要继续回答“为什么发生、人物如何选择、材料怎样支持这个判断”。所以结果不再是一段回答，而是一份可以保存和继续的 Exploration。

**设计选择**：不给聊天区最高视觉权重；中央时空画布是主角。

### Chapter 01｜定位：三个模式，一份研究上下文

#### Beat 01.1 — G01 一级导航

**聚焦**：顶部 `探索`。
**讲稿**：

> 探索是一级模块，因为它改变的不是一个侧栏，而是知识被组织的方式。时间柱、谱系星图和地图集回答已知结构；探索从一个尚未结构化的问题出发。

**默认**：探索高亮；退出时保留草案。
**异常**：草案未保存时先做离开保护。
**开发承诺**：独立 Explore 路由，不把旧工作台包进弹窗。

#### Beat 01.2 — G02 三态模式

**聚焦**：`编织态 / 播放态 / 书籍态`。
**讲稿**：

> 这不是三个产品。编织态用来把问题组织起来；播放态让历史变化发生在眼前；书籍态把作者的原文和论证送进同一装置。切换的只是视觉重心，时间、地点、当前 Claim 和证据引用都不丢。

**现场动作**：依次点亮三个模式，再回到编织态。
**开发承诺**：共享同一 `Exploration`，不是复制三份状态。

#### Beat 01.3 — G04 探索身份

**聚焦**：模式栏右侧探索名称和自动保存。
**讲稿**：

> 每一处生成内容都要知道自己属于哪个问题、哪本书、哪次草案。这里不是装饰性标题，而是研究身份：它决定范围、来源、私密性和恢复点。

**需在重做中解决**：当前顶栏同时显示“天宝九载”和靖难之役，语义冲突。发布前必须明确：顶栏展示全局浏览时间，还是本次探索时间；若两者并存，需显式命名，不得让观众猜。

#### Beat 01.4 — G03/G05 评审工具与环境

**聚焦**：主题、帮助、Presenter 入口。
**讲稿**：

> 澄与夜属于阅读环境，跟随系统；来源帮助负责解释证据等级。设计标注和 Presenter 只服务内部评审，真实用户不会看到开发编号和状态演示器。

**需在重做中解决**：现原型没有完整 G05 帮助入口；状态演示下拉也不应常驻真实产品壳。

### Chapter 02｜编织：让一句兴趣成为研究约定

#### Beat 02.1 — W01 研究约定

**聚焦**：左侧探索对话。
**讲稿**：

> 左边看起来像对话，但它的产品角色不是聊天记录。用户说“我想理解靖难之役怎样发生”，系统只追问一轮高价值问题，然后把时间、空间、对象和研究问题复述成一份可以修改的约定。确认之前，模型没有权力开始编历史。

**现场动作**：高亮时间 `1398—1402`、空间 `北平→南京`、对象。
**默认**：对话收起为研究约定摘要。
**交互**：只局部改时间、空间或主线；不清空整场。
**状态**：等待输入、待确认、已确认、范围冲突、范围过宽。
**开发承诺**：Brief 可以被播放态和书籍核对完整复用。

#### Beat 02.2 — 来源与编织流程

**聚焦**：`历史问题 / 私人书籍` 与 `范围确认→渐进编织→证据复核→时空探索`。
**讲稿**：

> 两个入口共享同一条可信工作流。先确认使用什么、明确不使用什么；再生成 6 到 12 个骨架场景；出处没有接好之前，节点只能显示待核，不能装作事实。

**状态演示**：在流程条内显示“正在建立骨架”，而不是用全屏模态遮住整个工作台。
**可取消**：已经完成的 Scene 保留。

#### Beat 02.3 — W02 叙事主线和时间骨架

**聚焦**：1398—1402 时间条与 `权力结构 / 军事推进 / 人物决策`。
**讲稿**：

> 同一批事实可以回答不同问题。我们不让模型交付一条唯一正确的长答案，而是把 Scene 组织成几条可以切换的解释主线。切换“军事推进”，改变的是阅读路径，不是偷偷改写事实节点。

**现场动作**：切换到军事推进；时间节点、地图路线和事件摘要同帧更新。
**状态**：推荐、用户选择、生成中、证据不足、已复核。

#### Beat 02.4 — W03 时空地图

**聚焦**：中央地图，依次亮起北平、济南、南京与路线。
**讲稿**：

> 这张地图不是历史风格的背景图。每一个点都来自可核验地点，每一条线都代表当前主线中的行动或影响。选择 Scene，地图自动给出范围；用户拖动地图，自动镜头立即暂停，把解释权交回用户。

**默认**：当前 Scene 居中、章节范围仍可见。
**交互**：点击地点、路线、人物；手动漫游暂停自动镜头。
**异常**：
  - 无可靠地点：保留上一范围并明确说明，不猜点；
  - 地名歧义：展示候选而不落点；
  - 瓦片失败：保留事件与坐标层，提供重试。
**生产承诺**：MapLibre 相机 + 已核验 raster 瓦片 + GeoJSON，不以当前 prototype raster 冒充生产地图。

#### Beat 02.5 — W04 事件详情

**聚焦**：地图下方当前事件卡。
**讲稿**：

> 地图负责“在哪里”，这张卡负责“这一刻为什么进入主线”。它只承载一个最小叙事单元：发生了什么、前因、当前作用、后续。我们故意不在这里塞满整段历史。

**现场动作**：从“燕王起兵”切到“燕军南下”，三段因果同步变化。
**状态**：史实、作者判断、模型推断、争议必须用不同标签。

#### Beat 02.6 — W05 证据透镜

**聚焦**：右侧证据。
**讲稿**：

> 右边不是“正方和反方”。材料可以互证，可以补充，可以讨论不同层级，也可能真的冲突。只有两个命题不能同时成立，我们才使用“直接冲突”。没有冲突时，界面有勇气留白。

**现场动作**：先亮“互证”，再亮“关注层级不同”，最后停在“尚无实质冲突”。
**异常**：出处失败只影响该证据卡，不遮住整个探索；关系待判定显示待核。

**章末接管**：`自己试试：切换一条主线或一个事件`。自由探索后按钮变为 `返回发布会 · 播放历史`。

### Chapter 03｜播放：让历史从知识变成过程

#### Beat 03.1 — 转场

**屏幕**：地图扩展成约 65% 视觉主体，侧栏退后。
**讲稿**：

> 当结构已经可信，我们不再让用户阅读一张静态总图。现在，历史按照 Scene 发生。

#### Beat 03.2 — P01 场景轨

**聚焦**：左侧六个 Scene。
**讲稿**：

> 场景轨不是完整事件目录，而是这条叙事主线的可读剪辑。已读、当前、未读一眼可见；存在分支时允许跳转，不强迫历史只有一条线。

**现场动作**：跳到“燕军南下”。
**状态**：已读、当前、未读、无地点、证据不足。

#### Beat 03.3 — P02 地图舞台

**聚焦**：整张地图和浮窗。
**讲稿**：

> 播放态把地图变成主舞台。镜头聚焦当前地点，保留前序路线，浮窗只说这一幕发生了什么。地图、浮窗、人物和时间必须在同一帧更新——不是四个组件各自刷新。

**现场动作**：从济南推进到南京；路线增长、当前点和浮窗同步。
**异常现场**：切回“建文削藩”：

> 这一幕没有单一可靠地点。我们保留上一空间范围并清楚说明原因，而不是为了动画完整随便猜一个坐标。

#### Beat 03.4 — P04 播放控制

**聚焦**：播放、步进、速度。
**讲稿**：

> 播放永远不夺走控制权。Space 播放暂停，左右键逐幕查看，手动点地图或场景会暂停自动推进。速度是阅读节奏，不改变 Scene 的历史时间。

**状态**：暂停、播放、缓冲、结束；减弱动态模式取消飞行。

#### Beat 03.5 — P05 时间带

**聚焦**：底部 1398—1402。
**讲稿**：

> 左边告诉你叙事顺序，下面告诉你它在真实时间范围中的位置。两处只共享一个当前时间，不允许出现“地图已到南京，时间仍停在 1400”的分裂状态。

#### Beat 03.6 — P03 解释透镜

**聚焦**：右侧当前 Claim 和两条材料。
**讲稿**：

> 每一幕都能被追问：这是材料确认的事实，还是史家的解释？这里比较的是命题之间的关系，而不是制造红蓝对打。制度解释和人物解释可以同时成立，因为它们回答的问题不同。

**章末接管**：`自己导演：暂停、回退一幕，再点一个地点`。返回点：`书籍也能进入同一装置`。

### Chapter 04｜书籍：忠实进入作者的历史世界

#### Beat 04.1 — B07 书籍身份和私密状态

**聚焦**：书名、章节、私人会话。
**讲稿**：

> 进入书籍态，研究对象从一个问题变成一本具体著作。书名、版本、章节、页码和私密性必须先出现。原文默认保留在个人空间；分享探索不等于发布整本书。

**状态**：本地、仅本次发送片段、已清除、准备导出。

#### Beat 04.2 — B01 来源切换

**聚焦**：内置阅读器 / 网页来源。
**讲稿**：

> 核心能力是内置阅读器，因为只有它能稳定保存页码锚点和段落联动。网页来源负责连续阅读和回到原站。对于微信读书，我们明确展示登录和跨域边界，不假装能够自动读取正文选区。

**现场动作**：切到网页来源，再回到内置阅读器。
**异常**：需登录、嵌入被拒、正文不可回流时，始终保留“在原站打开”和复制粘贴回流。

#### Beat 04.3 — B02 阅读器

**聚焦**：左侧书封、章节、页码和选中段落。
**讲稿**：

> 阅读没有被 AI 拆碎。用户仍然在连续阅读，只是任何段落都能成为探索入口。原文不被模型改写；点击段落，才启动右侧这一跳的结构化解释。

**现场动作**：从第一段切到第二段。
**状态**：解析中、可读、选区、缺页、文本层缺失。

#### Beat 04.4 — B03 段落到结构

**聚焦**：原文要点 → 作者观察 → 事件 → 人物/地点。
**讲稿**：

> 这是书籍态的核心翻译层。左边是原文，中间保留作者如何把材料组织成判断，再连接事件、人物和地点。作者观察必须写着作者的名字；模型推断必须可接受、驳回和改写，不能伪装成作者原意。

**现场动作**：选择“作者观察”，右侧透镜同步切换。
**状态**：原文直述、作者判断、模型推断、证据缺口。

#### Beat 04.5 — B04 书籍地图

**聚焦**：延安、西安、重庆和路径。
**讲稿**：

> 一本书同样拥有空间。地图不是整本书涉及地点的装饰性散点，而只显示当前段落和当前章节能够支持的位置。点延安，原文、论点和证据回到延安；点西安，系统明确告诉你这是补充材料地点。

**异常**：单地点、多地点、地名歧义、无可靠地点、范围过大。
**生产承诺**：当前 raster 只定义视觉目标；生产使用 MapLibre 的相机、图层排序、标签避让、移动/影响两种线型和来源可追溯 Geometry。

#### Beat 04.6 — B05 时间范围

**聚焦**：1937—1946。
**讲稿**：

> 书籍至少有三种时间：书中叙述的时间、史料写成的时间、作者回忆或写作的时间。这里先展示章节叙述范围；模糊年份保持模糊，绝不把“约 1942 年”伪装成某一天。

#### Beat 04.7 — B06 关系化证据

**聚焦**：作者视角、材料互证、不同解释。
**讲稿**：

> 我们忠实保存高华怎样解释整风，也按需补入互证材料和不同研究路径。不同不等于冲突：组织史、思想史和社会史可能是在补完同一幅图。只有同一 Claim 不可同时为真，才出现直接冲突。

**现场动作**：依次切换三类关系，停在“当前材料尚无实质冲突”。
**章末接管**：`自己阅读：选择另一段，看结构、地图和证据怎样一起改变`。

### Chapter 05｜信任：好的产品也要 proudly 地展示失败

异常不使用一个覆盖全局的通用弹窗演示。Presenter 要在失败发生的区域内切状态，同时保留其余已完成工作。

#### Beat 05.1 — Loading：渐进而不是等待

**位置**：编织流程条与首批 Scene 骨架。
**讲稿**：

> 系统先交付骨架，再逐条连接出处。用户能看到正在确定范围、建立骨架、链接出处、检查争议；可以取消，已经完成的 Scene 不消失。

#### Beat 05.2 — Empty：告诉用户下一步

**位置**：首次进入的中央画布。
**讲稿**：

> 空不是错误。它只提供两个高价值入口：提出一个历史问题，或导入一本私人书籍。没有功能清单，没有模型设置。

#### Beat 05.3 — Error：局部失败、整体可恢复

**位置**：右侧某一证据卡显示连接失败；地图和研究约定仍在。
**讲稿**：

> 一条外部证据失败，不应该抹掉已经确认的研究范围和事件骨架。这里可以重试、换来源或标记待补证；不会循环请求，也不会让模型补写缺失材料。

#### Beat 05.4 — Uncertain：不猜，就是产品能力

**位置**：地图显示上一范围；当前 Scene 明示“无可靠地点”。
**讲稿**：

> 不确定不是一个灰色感叹号，而是一条行为合同：保留什么、不显示什么、用户怎样继续。没有坐标就不上地图，没有材料就不制造反方，没有精确日期就不画成精确点。

**当前原型阻断**：状态下拉只有 Normal / Loading / Empty / Error，缺失 Spec 已承诺的 Uncertain；并且三个异常都使用同一个全局遮罩，无法证明“局部失败、成果保留”。重做必须补齐。

### Chapter 06｜收束：从发布会进入开发批准

#### Beat 06.1 — 回到全局

**屏幕**：三态缩略图不是三张图片，而是三枚可点击的实时状态卡；中央显示同一 Exploration ID、Brief、current Scene、selected Claim。
**讲稿**：

> 现在回看整个系统：一句问题在编织态成为研究约定，在播放态成为可理解的过程，在书籍态回到作者和原文。贯穿三态的不是一套配色，而是同一份可追溯的研究对象。

#### Beat 06.2 — 开发批准清单

按产品承诺而不是按文件列清单：

- [ ] **定位成立**：探索是一级路由，不是聊天外挂；
- [ ] **上下文连续**：三态切换不丢 Brief、Scene、Claim、Evidence；
- [ ] **研究约定成立**：生成前可确认时间、空间、对象和主线；
- [ ] **联动成立**：Scene 推进时地图、浮窗、场景轨、人物和时间同帧更新；
- [ ] **证据成立**：事实 100% 可回出处，作者判断有作者与页码，模型推断可驳回；
- [ ] **关系语言成立**：不强制正反；互证、补充、层级差异、冲突和缺口有明确条件；
- [ ] **地图成立**：无可靠地点不猜；生产图层、来源、镜头和失败降级已定义；
- [ ] **书籍成立**：内置阅读器可回原文；网页来源不声称跨域选区能力；
- [ ] **私密成立**：原文默认本地，导出不自动携带长篇文本；
- [ ] **异常成立**：Loading / Empty / Error / Uncertain 都保留可恢复上下文；
- [ ] **环境成立**：澄/夜、键盘、减弱动态、1440 主视口均通过；
- [ ] **边界成立**：原型资产不冒充生产地图，prototype 不冒充生产实现。

最终动作只有两个：

- `批准进入生产实现`
- `留下阻断意见`

不得用“整体看起来不错”替代逐项批准。

## 5. 自由探索与返回讲解

### 5.1 接管规则

- 每章末提供一次 `自己试试`，不是每个 Beat 都打断；
- 进入自由探索后，遮罩与 Presenter Card 消失，只保留折叠的 Chapter Rail 和底部 `返回发布会`；
- 原型在进入接管前保存 `tourCheckpoint`；
- 用户操作写入临时 `exploreBranch`，不污染确定性讲解状态；
- 点击返回时提供：
  - `带着当前选择继续`：把当前 Scene/段落作为下一章起点；
  - `回到讲解断点`：恢复 checkpoint。
- 90 秒无操作只提示一次，不自动夺回控制权。

### 5.2 导航与键盘

- `Space`：下一幕（处于地图播放控制时仍优先控制播放，Presenter 使用 `Enter`）；
- `← / →`：上一幕 / 下一幕；
- `Esc`：进入自由探索；
- `R`：回到讲解断点；
- `1–6`：跳章节；
- 点击 Chapter Rail 可跳章，Presenter 明确提示会重置为该章确定性初态。

### 5.3 状态不丢失的解释

Presenter 自己也必须遵守产品原则：跳章不是清空产品数据。它只切换一份隔离的 `presentationScenario`；真实用户草案和自由探索分支保持不变。关闭 Presenter 后，回到进入发布会前的 `returnState`。

## 6. 可直接实现的数据和组件合同

### 6.1 状态模型

```ts
type PresenterState = {
  active: boolean
  chapterId: "position" | "weave" | "play" | "book" | "trust" | "approval"
  beatId: string
  phase: "intro" | "focus" | "action" | "hold" | "free"
  checkpoint: ExplorationViewState
  returnState: ExplorationViewState
  exploreBranch?: ExplorationViewState
  rationaleOpen: boolean
  reducedMotion: boolean
}
```

### 6.2 Beat 合同

```ts
type PresenterBeat = {
  id: string
  chapterId: string
  mode?: "weave" | "play" | "book"
  target: string                  // data-presenter-id，不依赖 CSS 层级
  title: string
  claim: string                  // 台上主张，一句话
  script: string[]               // 最多三句
  rationale?: {
    productChoice: string
    rejectedAlternative: string
    stateContract: string
    acceptance: string
  }
  action?: PresenterAction        // 确定性点击或状态切换
  stateVariant?: string
  holdMs?: number
  allowTakeover?: boolean
}
```

### 6.3 组件边界

```text
PresenterLauncher
PresenterStage
  ├─ ChapterRail
  ├─ SpotlightMask
  ├─ PresenterCard
  ├─ LiveActionCue
  └─ TourProgress
StateScenarioController
ApprovalChecklist
```

- 产品区域只增加稳定的 `data-presenter-id` 锚点；
- Presenter 不复制业务 DOM，不维护第二套假的界面；
- `StateScenarioController` 注入 demo fixture，但使用真实组件状态；
- Presenter 文案与 Beat 配置独立，便于 PM 修改，不把长讲稿散进 JSX；
- 所有自动动作可取消；离开 Presenter 时清理 timer 和临时状态。

| G03 | 生产默认不存在 | 内部展开产品合同 | 评审数据缺失不影响业务 |

## 8. 本轮重做前的阻断项

这些不是美化问题，而是 Presenter 一讲就会暴露的产品矛盾：

1. **当前全局时间语义冲突**：顶栏“天宝九载 · 750”与靖难探索 `1398—1402` 同屏，未解释两者关系。
2. **Uncertain 未实现**：Spec 明确要求正常、加载、空、错误、不确定，现原型只有前四类。
3. **异常演示过于通用**：Loading / Empty / Error 都是同一全局遮罩，无法证明局部失败、已完成结构保留。
4. **G05 不完整**：主题存在，来源帮助和系统默认/时间 fallback 没有被产品化展示。
5. **标注不等于讲解**：现有卡片的“定位/默认/交互/状态/数据/验收”适合查表，但没有主张、被否决方案和跨区域联动演示。
6. **跨态连续性没有被证明**：当前三态切换主要更换 demo 状态，Presenter 必须展示同一个 Brief/Scene/Claim/Evidence 如何跨态保留。
7. **开发批准口径缺席**：原型 QA 写“passed”只证明实现与视觉对照，不等于 Product Manager 对产品逻辑的验收。

Presenter Mode 完成的最低验收：一位第一次看到项目的评审者，在不打开 Product Spec 的情况下走完发布会，能够准确复述五个产品命题，并能在最后的清单上指出每一项承诺对应屏幕上的哪次真实交互和哪种异常状态。
