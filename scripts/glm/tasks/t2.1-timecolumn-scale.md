# 任务：TimeColumn 渲染规模化——先诊断后虚拟化（T2.1）

## 背景与警示
方案原假设「TimeColumn 直接渲染 5,311 人」，但 E2E 实测 console 显示 `[TimeColumn] loaded 184 persons, 155 events`。
**不要按错误前提硬做虚拟滚动**——先诊断真实数据流，再决定动不动手、动多大。

## 第一步：诊断（必做，写进报告）
读 `frontend/src/components/timeline/TimeColumn.vue`（约 781 行）+ 它调用的 API/store：
1. 184 人是怎么来的？（哪个接口、什么参数、prefer_seed/limit 多少、按什么过滤）
2. 「朝代脉络」/「编年细览」两种模式各渲染多少 DOM 节点（人物条 + 事件卡 + 刻度）？
   给出实测计数方式（如在浏览器 console 用 document.querySelectorAll 统计——服务已跑在 :5174，
   可用 Playwright 脚本实测，参考 frontend/e2e/ 里的写法）
3. M4 之后事件将从 122 → 300+、人物条可能全量放开：当前实现的 DOM 增长是线性的哪一部分？

## 第二步：按诊断结论行动（三选一，报告里说明选择依据）
- **A. 若当前最重模式 DOM 节点 >800**：实现列表虚拟化（只渲染视口±缓冲区；不引入第三方库，
  用 IntersectionObserver 或 scroll+transform 手写；保持现有交互：点击选中、hover、年份跳转、模式切换）
- **B. 若 DOM 可控但存在明显的 O(N) 重复计算/重排**（如每次年份变化全列表重算样式）：做针对性优化
  （computed 缓存、CSS containment、避免整列表 re-render），并留一个「数据量翻 3 倍」的防线说明
- **C. 若两者都不成立**：不改代码，交一份规模化预案（何时触发虚拟化、改哪里、预计工作量），
  存 `docs/perf-notes.md`
无论选哪个：`content-visibility: auto` / `contain` 这类零风险 CSS 若适用可顺手加。

## 边界
- 只改 `frontend/src/components/timeline/**`、`frontend/src/styles/**`、（选 C 时）`docs/perf-notes.md`
- 不改接口、不改 store 结构、不新增依赖；不 git commit/push
- 现有 E2E（frontend/e2e/timeline.spec.js）必须保持绿

```bash
cd frontend && npm run build && npx playwright test --reporter=line
```
