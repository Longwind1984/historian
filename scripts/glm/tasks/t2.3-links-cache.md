# 任务：/api/links/* 扫描结果缓存（T2.3）

## 目标
`/api/links/global` 当前**每次请求**对 7,010 实体 × 全名字索引做 mention 扫描，冷热一样 2.6s。
目标：热请求 <100ms；数据文件变化后自动失效重建。

## 现状（先读懂再动手）
- `backend/app/api/links.py`（约 374+ 行）：NameIndex 已有进程内单例缓存（_INDEX，_built 标志），
  但 `/links/global`、`/links/scan/{id}`、`/links/backlinks/{id}`、`/links/count/{id}` 每次调用时的
  **mention 扫描**（正文 × 名字匹配）没有缓存
- `backend/app/core/data.py` 已有通用缓存模式：`_get_cached(key, loader_fn, dir_path)` 用目录签名
  (最新 mtime, 文件数) 判失效——**复用这个模式**，别再造一套

## 实现要求
1. 启动后首次请求时构建一次全量 mention 图（实体→出链列表 + 反向入链索引），进程内缓存；
   用与 data.py 一致的目录签名策略对 `DATA_DIR` 失效
2. `/links/global`、`/links/scan`、`/links/backlinks`、`/links/count`、`/links/search` 全部改为查预建图/索引
   （search 若本就是独立逻辑可不动，报告说明）
3. NameIndex 的失效也要挂到同一签名（当前 _built 一旦 true 永不重建——数据改了它不知道）
4. 首次构建时间打日志（logger 或 print 一行），并在报告里给出实测值
5. 不改任何 API 的响应结构（有 pytest 合同测试锁着）

## 边界
- 只改 `backend/app/api/links.py`（如需小工具可放 `backend/app/core/`）
- 不新增依赖；不 git commit/push
